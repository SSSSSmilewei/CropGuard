# PPT 权重修正 + 业务逻辑/技术补充大纲
### 依据：2026 睿抗《AI 视觉应用赛题规则文件》+ 现有《路演汇报PPT FIN》（21 页）

> 用途：给路演同学一份"照着加就行"的清单。
> 原则：**不动他的叙事风格，只调权重、补内容、改口径。**
> 一句话：现在这套稿子像"创业路演"，评委按"工程验收"打分——**叙事没错，配比错了。**

## 0 先解决一个误会：业务逻辑 ≠ 技术实现

路演同学说"业务逻辑就是技术实现"，这是分歧的根源。给他两个一句话判据，比讲定义管用：

> **判据一：把模型换掉，这套规则还成立吗？成立的部分就是业务逻辑。**
> 换成别的检测器，"高风险 → 片区A 喷 3 秒 → 人确认"依然成立 → 这是业务逻辑。
> "单图 112 ms、ONNX 640" 换了模型就变 → 这是技术实现。

> **判据二：评委问"为什么是 3 秒"，答案在配置表里还是模型里？**
> 在配置表里 → 业务逻辑。在模型里 → 技术实现。

### 一张对照表（同一件事的两种说法）

| 事 | 技术实现的说法（他会讲） | 业务逻辑的说法（评委想听） |
| --- | --- | --- |
| 识别 | YOLOv8s，27 类，mAP 76% | 系统替人回答"这是什么虫、有几只、在哪" |
| 分级 | `assess_risk()` 三个统计量 | 把"虫口密度"翻译成"该不该动手"的**农艺口径** |
| 剂量 | `risk_map` 查表 | 高风险整片 3 秒、中风险单片区 2 秒、低/无风险**不喷** |
| 防误喷 | 三个 if | 高风险**且**建议施药才生成指令；**人点片区、人按下发** |
| 留痕 | 写 jsonl | 每一次"打没打、打哪、打几秒、谁按的"都可追溯 |

### 最好用的一条类比线（他不需要懂代码也能讲）

**把系统讲成"下田的赤脚医生"**：

| 系统环节 | 医院类比 |
| --- | --- |
| 摄像头/手机采集 | 化验取样 |
| 27 类检测模型 | 化验单：是什么、多少、在哪 |
| 风险分级 | 诊断：轻症 / 重症 |
| 知识库 + 本地大模型 | 处方建议（**只开方，不抓药**） |
| 双因素判真 | 两道签字：诊断够重 **且** 处方写了用药 |
| 人工确认 | 患者签字同意 |
| 喷淋执行 | 打针（**不可逆**，所以必须签字） |
| 历史记录 / 看板 | 病历 |

> 这条路演同学能独立讲 3 分钟，且完全不需要解释 YOLO。
> 关键收尾句：**"我们做的不是一台更准的相机，是一个能开方、但把针头交给人按的村医。"**

## 1 用评分表倒推：现在权重错在哪

### 1.1 总决赛 100 分的真实构成

| 评分项 | 分值 | 性质 |
| --- | --- | --- |
| 实测推理准确度（20 样本逐张判） | 20 | **现场可验** |
| 推理时效性（180 秒） | 10 | **现场可验** |
| 采集质量与输入标准化 | 15 | **现场可验** |
| 样本与数据源真实性 | 10 | **现场可验** |
| 系统稳定性（每次人工干预扣 5 分） | 10 | **现场可验** |
| 场景化反馈机制（物理动作或信号反馈） | 5 | **现场可验** |
| 商业价值与路演表现 | 15 | 其中"创新与落地"仅 **7 分** |
| 赛程延续性（上一阶段 ×15%） | 15 | 与 PPT 无关 |

**结论：70 分靠现场工程能力，只有 7 分靠"商业价值包装"，8 分靠临场表达。**

### 1.2 现稿的页数分布（21 页）

| 内容块 | 页码 | 页数 | 对应评分项 |
| --- | --- | --- | --- |
| 需求性 / 根属性 / 痛点 / 根因 | S3–S10 | **8** | 0 分（初赛才考立意） |
| 方法论（对齐颗粒度、四层架构） | S11–S13 | 3 | 间接 |
| 解决力（112ms / 27 类 / 决策四步 / 对比表） | S14–S17 | 4 | 部分对应 |
| 损益比（成本收益） | S18–S19 | 2 | 7 分 |
| 边界 + 结尾 | S20–S21 | 2 | — |

**8 页讲"为什么要做"，4 页讲"做成了什么"，0 页讲"怎么运转的"。**
而赛规对形态 C 的原话是：

> "此类场景需**重点体现复杂的业务逻辑处理能力与系统集成度**，避免仅展示单一的屏幕画面，
> 须包含明确的物理反馈机制或外部设备联动。" ——《规则文件》五、竞赛任务 · 形态C

**这句话就是本次修改的授权书。** 不是我们要加技术，是赛规点名要求"业务逻辑 + 系统集成度"。

### P5 · 一条虫情事件的完整旅程（业务流程图）

**标题**：从"看见一只虫"到"喷头动一下"，中间经过 7 道关

**版式**：横向 7 步泳道图，每步标"谁做 / 耗时 / 失败会怎样"

```
① 采集        ② 识别        ③ 分级        ④ 建议        ⑤ 人确认      ⑥ 下发        ⑦ 回读留痕
双路相机/手机 → 27类检测 → 规则定级 → 知识库+本地LLM → 人点片区 → CGP协议 → /status+历史
 10–20ms      112ms       <1ms       0–300ms(异步)   人工        20–40ms      实时
 掉线→看门狗   无目标→0只   三档风险    未命中→拒答     不点→不喷    节点离线→语音  写 jsonl/看板
```

**口播（30 秒）**：
> "评委看到的是一张带框的图，但系统真正跑的是这七步。
> 请注意第 5 步——**整条链路唯一必须由人完成的动作**。前面六步全自动，
> 唯独'按下发'交给人，因为识别错了可以重拍，喷头动了收不回来。"

**对应评分项**：场景化反馈机制（5）、答辩"技术理解"（8）

### P6 · 八条硬规则（业务规则表）

**标题**：剂量不来自模型，来自这张表

| # | 规则 | 取值 | 为什么 |
| --- | --- | --- | --- |
| 1 | 风险分档 | 高 / 中 / 低 / 无 | 三档够用，四档现场讲不清 |
| 2 | 高风险剂量 | 全片区 `all`，**3 秒** | 虫口已扩散，单片区压不住 |
| 3 | 中风险剂量 | 单片区 `g1`，**2 秒** | 点状发生，只处理确认片区 |
| 4 | 低/无风险 | **不喷**，只出报告 | 减药是硬约束 |
| 5 | 单次上限 | 服务端 5 秒 + 固件 5 秒 | **双上限**：配置写错也喷不长 |
| 6 | 自动节流 | 同片区 3 秒内不重复 | 雾化片怕连续通电 |
| 7 | 触发条件 | 高风险 **且** 建议施药 | 模型可以判高，但建议说"先物理防治"就不喷 |
| 8 | 最终确认 | 人点片区、人按下发 | 执行不可逆，责任必须落到人 |

**口播（40 秒）**：
> "这八条里，没有一条是模型算出来的。模型只负责'是什么、有多少'；
> **打不打、打哪、打几秒，全部查表**。这张表在配置文件里，改一行就改行为，不用重训模型。
> 这也是我们敢在现场演示的原因——**行为是可预期的**。"

**对应评分项**：答辩"技术理解"（8）、系统稳定性（10）

**接口清单（只列 6 条，够证明集成度）**：

| 方向 | 协议 | 端点 | 用途 |
| --- | --- | --- | --- |
| 浏览器 → 服务 | WS | `/ws/stream` | 推画面 + 检测结果 |

**对应评分项**：系统集成度（形态C 点名）、系统稳定性（10）

### P8 · 时间都花在哪了（时延预算 + 并发）

**标题**：机器只花 2.2 秒，剩下 178 秒留给人

| 环节 | 典型耗时 |
| --- | --- |
| 采集与解码 | 10–20 ms |
| 预处理（letterbox 640） | 2–4 ms |
| **模型推理** | **112 ms** |
| 后处理（阈值 + NMS） | 1–3 ms |
| 风险分级（纯规则） | < 1 ms |
| 指令下发 + 继电器 | 20–40 ms |
| **关键路径合计** | **约 145–180 ms** |
| 20 个样本纯机器耗时 | **约 2.2 s / 180 s** |

**右下角补两个"集成度"数字**（这是加分点，不是炫技）：
- **多客户端共享一路相机**：手机 + PC 同时看，只开一个采集源、只跑一份推理（不是各开一个）
- **推理与推流解耦**：推理 5 fps、推流 15 fps，画面跟手但不算力翻倍

**口播（30 秒）**：
> "180 秒里，机器只占 2.2 秒。这不是我们快，是**把时间留给了人**——
> 递样、取景、确认，这些才是现场真正花时间的。
> 反过来说，就算现场电脑慢一个数量级，我们仍然在时限内。"

**对应评分项**：推理时效性（10）——**这页把 10 分从"我们的数字"变成"我们的预算"**

### P9 · 出故障的时候，系统还剩什么（降级矩阵）

**标题**：喷头坏了，系统仍然有价值

| 失效环节 | 表现 | 降级方案 | 仍然保留的能力 |
| --- | --- | --- | --- |
| 施药执行 | 泵不动作 / 节点离线 | 语音播报 + 界面报警 | **场景化反馈**（评分口径允许"物理动作**或**信号反馈"） |
| 本地大模型 | 未加载 / 超时 | 直返知识库原文并标注来源 | 建议能力（措辞降级，内容不降级） |
| 相机 | 掉线 / 冻结 | 看门狗自愈 → 强制重开 → 切手机入口 | 手持识别路径 |
| 网络 | 热点切换 / 网段变化 | 节点 DHCP + 串口读 IP + 页面热更新地址 | 本地闭环 |
| 检索 | 未命中 | 统一拒答，提示扩展知识库 | 不产生错误建议 |

**口播（30 秒）**：
> "这张表是我们主动准备的，不是被问出来的。
> 比如喷淋彻底失效——按评分口径，'物理动作**或**信号反馈'满足其一即可，
> 我们的语音和界面报警就是保底通道，**闭环不会整体哑火**。
> 系统的价值在于把'该不该打、打哪、打多久'判断清楚，喷头只是末端。末端可换，判断不可替代。"

**对应评分项**：系统稳定性（10）、临场答辩（8）、场景化反馈（5）
